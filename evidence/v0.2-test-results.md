## 2. 新增真正经过原生 Proxy 的边界

HTTP → GatewayIngress → 未 fork 的 LiteLLM Proxy → 原生 PostgreSQL virtual key → 原生 Router/provider → 本地 TCP mock：

- 主429后备用，主备收到完全相同、顺序不变的四条历史和输出上限37；明确两次实际调用
- 两次慢上游共用1.2秒总预算，返回504、没有第三次尝试；取消释放后下一请求正常
- 连续SSE分片没有触发空闲超时，但被总时限截断；不出现 DONE/stop、不切备用，随后恢复
- 正常stop、length、同一非空文本delta上的refusal，线级语义、attempt_finished与request_finished一致
- 完整响应后到达的ASGI disconnect不再覆盖终态；真实提前断开仍取消并释放资源
- 文字后的独立refusal-only分片确实丢失，明确保留为已知上游限制

每个新原生进程先做真实合成warmup，等待请求/审计/上游全部清理，再重置故障计数，避免冷启动成本把“第二次尝试”测试变成只有一次调用的错误断言。没有放宽两次调用或终态断言。

## 3. 恢复和进程生命周期

[原生恢复证据](native-recovery.json) 独立记录 **107.463 秒** 的实际演练：

1. 创建短期原生合成key，新旧并行可用；撤销旧key
2. drain并重启到B，再回到A；检查实际revision、DB就绪、真实路由由secondary回primary；旧key持续拒绝
3. 记录主池实测零额度及原next_probe；备份里保留两把活跃key
4. 真正pg_dump/pg_restore到新兄弟库，86张表、396行内容一致，189项migration完成
5. 备份后撤销其中一把key；真的停止PostgreSQL，缓存有效key仍503且零上游
6. 数据库回来后，因必要审计曾失败，原进程保持失败关闭；明确重启代理后才恢复
7. 还原库保持drain：备份前已撤销key仍拒绝；备份后才撤销的key确实复活；重新撤销、再次重启后持续拒绝
8. 有效key恢复推理，只走secondary，已耗尽primary零调用；额度与原reset没有被补满/推迟
9. 两库剩余合成key全部撤销；进程和临时PostgreSQL干净停止，临时目录/dump删除

快照内容证据单独在 [database-recovery.json](database-recovery.json)。其中`excludes.restored proxy authentication`仅表示该小函数本身不测鉴权；鉴权在上述独立原生生命周期阶段验证，不能混淆两个证据层。

该演练不包含Docker CLI事务、Nginx、Mac、跨版本迁移或自动完整撤销日志恢复。正式恢复仍必须核对备份后全部权限/撤销变化。

## 5. 环境、复现及保留警告

Linux x86_64；Python3.12.14；LiteLLM1.104.0；OpenAI SDK2.54.0；PostgreSQL17.11；Prisma Python0.15.0/CLI5.17.0；Node24.19.0。版本/lock没有升级。

```sh
LITELLM_LOCAL_MODEL_COST_MAP=True \
  .venv/bin/python tests/run_postgres_suite.py --postgres-bin /path/to/postgresql/17/bin
```

runner仅创建新临时数据库。使用已经安装的匹配工具；本交付没有安装Docker守护进程。`--skip-backup-restore`会跳过两类恢复演练，不是通过。工具下载/源访问按环境批准规则执行。

上游警告包括Pydantic ReadOnly/deprecation和可选Prometheus cooldown callback未await。未隐藏、未视作功能通过证据，也没有为消除警告修改上游包。自身持久化冷却经过独立await和回归。

## 6. 开发中发现并修正

- 实际DB中断后不能自动恢复的初始测试假设不符合有意的审计失败保护：修正测试/手册，保留安全锁，不修改成自动放行
- 新原生进程deadline测试最初受冷启动干扰：加入明确warmup与资源释放，不放松断言
- 新完整流审计断言揭示晚到disconnect覆盖终态：修正响应完成标记和取消处理，并新增stub/真实Proxy双层回归
- key helper旧测试在接口迁移中更新为显式环境目标；最终完整快照已统一通过

真实账户、实际消费应用及部署环境门槛继续保留，仍是V0.2工程候选。
