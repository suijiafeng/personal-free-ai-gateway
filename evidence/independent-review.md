## 重点检查与修正复验

1. **每次实际尝试的约束**（§1.3、§5.3、§9.4、G-02、AT-07/15/16/24）：免费资格、复核时效、部署授权、隐私和能力在筛选及每次部署调用前校验；实际模型、地址与生产凭据引用绑定。模拟收费、未知资格、未授权备用和路由覆盖路径的调用数为零。生产模板没有已启用供应商。
2. **流事件后的禁止切换**（§8.2、AT-05）：原生 1.104.0 仅凭生成内容判断能否切换，角色事件不能自动满足原规格。扩展在任意 typed 事件/输出字节后关闭新尝试。角色后、正文后异常，以及干净 EOF 场景已测试；不拼接第二模型，不返回伪造的成功终态。
3. **真实结束事件的来源**（§8.2、AT-04/05）：独立直接调用原生 SDK 复现了“干净 EOF 被补成 stop”。正常 mock 流触发真实终止 deployment hook，而不完整 EOF 的合成终止不触发。扩展利用此来源差异，在输出合成终止之前拒绝它；原生 Proxy 线级测试确认没有 `[DONE]` 或伪 stop。
4. **用量不是零**（§1.3、§8.1、§11.2、AT-09）：独立复现原生非流缺失 usage 被转换为 0/0/0，以及流 hidden usage 被合成。当前扩展统一输出 null/unknown，避免冒充上游实测；这同时意味着真实 usage 的有来源保留尚未完成。
5. **次数和全程时限**（§9.2、§12.1、AT-12）：原生 SDK/Router 额外重试关闭，最多两次生成尝试。首次复核发现分块慢上传能绕过总时限；修正后同一 40ms 预算测试在约 41ms 返回 504，并释放本地槽位。
6. **共享状态与持久化**（§10.3/10.4、AT-13/14/23）：首次复核发现旧请求成功会清除更新的 429 冷却；修正后活动冷却被保留，引用计数避免删除另一请求的占用。真实 PostgreSQL 新状态实例重载保留冷却，缺失池保持未知；这不是完整服务/DB 进程重启验收。
7. **吞掉的 hook 错误**（§12.3、AT-18/21）：原生成功/失败 deployment callback 会吞异常。扩展提前设置 audit/state 失败标志，并在后续尝试和 ASGI 响应边界检查；注入存储失败不会默默继续备用或被当作完整成功。流前失败造成的池占用泄漏亦已修正复测。
8. **身份、日志与取消**（§12、AT-17/18/19/22/23）：完整原生 Proxy/DB 测试覆盖受限 key 创建/撤销、主密钥不能推理、未授权备用、实际 TCP 取消及后续恢复、第三个并发请求有界拒绝。恶意上游错误中的提示词/密钥 sentinel 未进入公共响应、stdout/stderr、追踪或原生 ErrorLogs/SpendLogs。DB 配置覆盖和状态库不可达均在新上游调用前失败。

- **用量、余额和诊断**：下方追加范围已经补齐经证实的非流 usage、来源/维度/时效/耗尽观察、时区规则和私有只读诊断。流式与 Gemini 用量仍未知；Groq 原生非流路径丢失响应头时不得制造余额。真实账户余额语义、逐请求完整候选排除原因及六个完整 UI 页面仍不是已完成承诺（AT-09/13/18，§13–16）。

## 上游警告的影响

独立非 DB 运行有 9 条上游警告，DB 运行有 7 条，包括 Pydantic schema/deprecation 警告，以及 `router_cooldown_event_callback` 未 await 的 RuntimeWarning；不能宣称 warning-free。

检查锁定版本源码可见：原生 cooldown handler 先更新 cooldown cache，再调度该 coroutine；该 callback 用于 Prometheus 冷却/不可用指标。本项目没有配置 Prometheus，自己的共享池冷却通过独立、await 的 PostgreSQL 写入和逐尝试检查执行，并已复测。因此当前证据将此项归为上游可选指标警告，没有复现为免费资格、两次预算或持久化冷却绕过。升级时应重新验证，不为消除警告而 fork 或改写供应商源码。

**可交付的是源码、可复现测试与带边界的验证证据；不能把它描述成已接真实免费账户、已完成全部验收或已部署上线的服务。**

## 最终追加复核：额度、来源、诊断与真实恢复

最终使用仓库 `tests/run_postgres_suite.py` 从全新 UTF8 PostgreSQL 17.11 临时目录启动。该 runner 自动生成锁定原生 Prisma client、执行 189 项 migration、8 项恢复保护测试、完整 tests/ops，然后进行同版本数据库备份恢复。独立执行退出码 0；pytest 为 **416 passed、19 subtests passed、26 warnings，27.86 秒**。8 项恢复保护测试另外计数。临时 PostgreSQL 已停止、临时目录及 dump 已删除。

新增范围经过源码检查、独立模块测试和最终真实 Proxy/DB 全链路复跑：

- 经官方 `log_post_api_call` 的原始响应元数据证明，OpenAI/Groq 非流真实 usage 与缺失 usage 可以区分；只保留必要数值，不记录原始响应。回调部署 ID 必须匹配当前尝试，备用前清空旧元数据。流式/Gemini 没有可证来源时继续 unknown，不借用原生合成用量。
- 额度观察包含供应商、账户、模型、计量维度、窗口、时区、来源、观察时间与过期时间；Groq 日请求与分钟 Token 不合并，Gemini 太平洋时间午夜规则覆盖夏令时边界。已过期观察不补为满额。
- 实测零余额和可信恢复时刻分开处理。缺少 reset 时使用明确标注的本地观察过期策略暂停，reset 保持 null；到期仅允许受控探测，不保证恢复额度。旧成功不能清除新冷却/耗尽，晚到的零观察也不能覆盖持久化的凭据停用状态。
- 持久化池状态绑定账户/模型/窗口等范围指纹；复用 ID 后更换范围不能继承旧状态。连接显式强制 UTF8，避免客户端编码导致字节 ID。
- 管理资源/配置/汇总/按请求查询均为只读、管理员专用，不触发模型调用。消费者入口和 Nginx 声明仍不开放这些路径；响应不暴露凭据或原始供应商地址。
- 调用 key 标识改为真实凭据的一向指纹，不依赖可重复/缺失的 alias；拒绝重复 Authorization、Content-Type、Content-Length，避免不同层对身份/报文边界的不同解释。
- 真正执行 `pg_dump` 到新 sibling 数据库的 `pg_restore`，按一致性快照比较 86 张表的行数及内容摘要，包含 189 项 migration、额度观察和原生 key 表。没有覆写现有数据库，也没有把“可读备份文件”冒充恢复成功。该证据不包含恢复后 Proxy 鉴权或跨版本恢复。

### 复跑中发现的测试时序问题

首次扩大范围的独立运行曾得到 415 passed、1 failed：并发测试在 warmup 响应已到达、审计清理尚未释放槽位时，把 warmup 的槽位误当成两条新请求之一。没有由此证明网关同时执行了超过两次请求。测试已改为等待 warmup 完全清理，并用释放事件明确保持两条真实上游请求，再验证第三条 429。没有放宽断言或靠重跑掩盖失败；网关并发代码未因该测试问题修改。上述最终新库全量复跑是在更强的确定性测试上通过的。

最终仍有上游 Pydantic 和可选 Prometheus 冷却 callback 警告，影响范围如上节；不宣称 warning-free。真实账户、实际消费应用和部署环境门槛仍然保留，生产供应商仍默认停用。
